# دليل العمل: بناء المشروع بـ Claude Code

الفكرة: وثيقة التصميم هي مصدر الحقيقة. منها تُستخرج مواصفة (Spec) لكل شريحة رأسية. كل شريحة تُنفذ على فرع خاص بها، وفيه Commit لكل خطوة. وكل Commit لازم يعدي من `make check`.

```
docs/design.md  ──/extract-spec──►  specs/SXX-*.md  ──/implement-slice──►  feat/SXX-*  ──PR (rebase)──►  main
       ▲                                   │                                      │
       └──────── ADR / تعديل التصميم ◄────────┴──────────── قرار جديد أثناء التنفيذ ◄──┘
```

---

## 1. الإعداد لأول مرة (مرة واحدة)

```bash
git init -b main && git add -A && git commit -m "chore(repo): add starter repo"
make setup                       # uv sync + git hooks (pre-commit + commit-msg)
make up && make check
gh repo create --private --source . --push
```

على GitHub (مرة واحدة):
- احمِ فرع `main`: PR إجباري، والفحوصات `check` و`integration` و`commits` لازم تنجح، وتاريخ خطي (Linear history)، ومنع الـ Force push.
- طريقة الدمج: **Rebase and merge** فقط.
- فعّل حذف الفرع تلقائيًا بعد الدمج.

افتح Claude Code في المجلد، واكتب `/context` لتتأكد إنه حمّل `CLAUDE.md`. واكتب `/hooks` لتتأكد إن الـ Hooks الثلاثة موجودة.

## 2. استخراج المواصفات من وثيقة التصميم

### لماذا لا نطلب "اكتب Spec" مباشرة؟
الـ Agent لو قرأ الوثيقة كاملة واخترع المواصفة، هيعمل حاجتين وحشين: يسقط جمل من التصميم من غير ما ياخد باله، ويخترع أرقامًا مش موجودة. الطريقة دي بتمنع الاتنين:

1. **خريطة الشرائح أولًا (`specs/README.md`):** كل شريحة مربوطة بأقسام محددة من الوثيقة، ومعاها ترتيب الاعتماديات. الخريطة دي موجودة، فراجعها مرة واحدة.
2. **قراءة محدودة:** الـ Skill `extract-spec` بيقرأ الأقسام المذكورة للشريحة بس، والـ ADRs المرتبطة، وقسم **Interfaces** من الشرائح اللي بيعتمد عليها. مش الوثيقة كلها.
3. **تغطية كاملة بلا اختراع:** كل جملة متطلبات في الأقسام دي لازم تقع في مكان واحد من التلاتة: معيار قبول (AC)، أو "خارج النطاق ← شريحة أخرى"، أو "سؤال مفتوح". وكل AC عليه وسم مصدره `[D: العنوان]`.
4. **التناقضات تتحول لأسئلة لا لقرارات:** لو الوثيقة ساكتة أو قسمين بيتعارضوا، الـ Agent يكتب سؤالًا فيه القراءتين واقتراحًا افتراضيًا، ومايختارش بنفسه.
5. **مراجعة بعين جديدة:** الـ Subagent `spec-reviewer` (سياق نظيف) يطلع: الناقص، والمتناقض، والمخترع، والمعايير اللي مش قابلة للاختبار.
6. **أنت تجاوب الأسئلة المفتوحة** قبل التنفيذ. وأي إجابة بتغيّر التصميم تتسجل في الوثيقة أو في ADR.

### الخطوات الفعلية
```text
# جلسة جديدة، Plan mode (Shift+Tab)
/extract-spec S06
```
بعدها:
- راجع ملخص التغطية والأسئلة المفتوحة.
- جاوب كل سؤال جوه ملف الـ Spec نفسه: `- [x] Q1 — … (resolved by: <اسمك>, <التاريخ>): <القرار>`.
- لو القرار بيغيّر التصميم: `/write-adr <title>`، أو عدّل القسم في `docs/design.md`.

> المواصفات الـ 23 (S00–S22) مكتوبة بالفعل كمسودات أولى بالطريقة دي، وفيها أسئلة مفتوحة حقيقية لقيتها
> في الوثيقة. أمثلة: S02 Q1 (حافة في الرسم مش موجودة في الجدول)، وS04 Q1 (CAMeL Tools مقابل نقاء الـ Domain)،
> وS07 Q1 (حد الحجم مع Presigned PUT). شغّل `/extract-spec SXX` لما الوثيقة تتغير، أو لو حابب تعيد توليد شريحة.

## 3. تنفيذ شريحة: الدورة الكاملة

### أ. قبل البداية
- كل الشرائح في `Depends on` اتدمجت في `main`.
- الأسئلة المفتوحة في الـ Spec اتجاوبت كلها.
- **جلسة Claude Code جديدة** (`/clear` أو نافذة جديدة). شريحة واحدة في كل جلسة.

### ب. التنفيذ
```text
/implement-slice S06
```
الـ Skill ده بيمشي بالترتيب ده:
1. ينشئ الفرع `feat/S06-postgres-job-queue` من `main` المحدّث.
2. يعمل Commit للـ Spec (لو جديدة أو اتعدلت)، ويفتح Draft PR.
3. يكتب خطة ويستنى موافقتك. **اقراها بجد:** ده أرخص مكان تصلّح فيه الاتجاه.
4. يكتب كل اختبارات القبول بعلامة `xfail(strict=True)`، ويعمل Commit.
5. خطوة خطوة حسب **Commit plan**: يكتب الكود، ويشيل `xfail` عن الاختبارات اللي نجحت، ويشغّل `make check` (والـ Stop hook بيفرضه)، ويعمل Commit بالرسالة المكتوبة في الـ Spec، ويعمل Push.
6. يشغّل المراجعين الثلاثة (معمارية، وأمان لو الشريحة لازمة له، واختبارات)، ويصلّح الملاحظات المؤثرة في Commit واحد.
7. يحدّث وصف الـ PR بالأدلة، ويحوّله لـ Ready.

### ج. دورك أنت
| متى | ماذا تراجع |
|---|---|
| بعد الخطة | هل الخطة بتغطي كل AC؟ هل في حاجة زيادة عن الـ Spec؟ |
| بعد Commit الاختبارات | **أهم مراجعة:** هل الاختبارات بتثبت المعايير فعلًا؟ (بعد كده ممنوع تعديلها) |
| الشرائح الحرجة (S02، S03، S06، S09) | كل سطر SQL متزامن، وكل انتقال حالة، وكل مفتاح |
| قبل الدمج | جدول المراجعين، وCI أخضر، ومفيش `reason="S06"` فاضل |

### د. لو الـ Agent بيلف في مكانه
- صحّحته مرتين في نفس النقطة ولسه غلط؟ `/clear` وابدأ جلسة جديدة بطلب أدق: "أكمل S06 من الخطوة 5. الوضع الحالي: …".
- الـ Spec نفسه طلع غلط؟ وقّف، عدّل الـ Spec في Commit مستقل `docs(S06): clarify lease renewal on handoff` مع السبب، وبعدين كمّل.

## 4. استراتيجية الفروع والـ Commits بالتفصيل

### الفروع
- `main`: محمي، أخضر دائمًا.
- `feat/SXX-<slug>`: شريحة واحدة، عمرها من يوم لـ 3 أيام، و`rebase` على `main` يوميًا.
- `spike/S00-...`: للتجارب، ويتدمج منه docs وnotebooks وADRs بس.
- `fix/<short>` و`docs/<short>`: لإصلاحات وتوثيق خارج الشرائح.

### لماذا Commit لكل خطوة، ولماذا xfail؟
- كل Commit صغير ومفهوم، وتقدر ترجع له أو تعمل `git bisect` عليه.
- الاختبارات بتتكتب الأول (TDD)، لكن كده المفروض إنها تفشل، والـ Stop hook مايسمحش بإنهاء أي مهمة وفي اختبار فاشل.
  الحل: `xfail(strict=True)`. الاختبار متوقَّع فشله فالحزمة تفضل خضراء. ولو نجح وهو لسه معلّم، `strict` يفشّل البناء، فتضطر تشيل العلامة في نفس الـ Commit اللي خلاه ينجح. بكده كل Commit بيوثّق بالظبط أنهي معايير اتحققت فيه.

### شكل التاريخ المتوقع لشريحة (مثال S06)
```text
$ git log --oneline main..feat/S06-postgres-job-queue
a1f9c02 fix(S06): address review findings
93be417 feat(S06): add worker loop with cancellation
7c2d0e1 feat(S06): add reconciler
4e81b6a feat(S06): add heartbeat and fenced complete
2b0f7d3 feat(S06): claim with FOR UPDATE SKIP LOCKED
d77c1a8 feat(S06): add queue and clock ports with fakes
1a6e2f4 test(S06): add queue contract and chaos tests (xfail)
0c3b9e5 docs(S06): add spec
```
وبعد الدمج بـ "Rebase and merge"، نفس الـ Commits دي بالظبط تظهر على `main`.

### رسالة الـ Commit
```text
feat(S06): add heartbeat and fenced complete

Late results from a worker that lost its lease must not overwrite a newer attempt.

Spec: specs/S06-postgres-job-queue.md
```
الـ Hook المحلي والـ CI بيرفضوا أي رسالة مش ماشية على الشكل ده.

### العمل بالتوازي
بعد دمج S01، الشرائح S02 وS03 وS04 وS07 مستقلة عن بعض:
```bash
git worktree add ../te-S02 -b feat/S02-job-state-machine
git worktree add ../te-S04 -b feat/S04-arabic-text-normalization
# جلسة Claude Code منفصلة في كل مجلد
```
ادمج بترتيب الجدول. وأي فرع لسه مفتوح يعمل `rebase` بعد كل دمج.

### الإصدارات
في نهاية كل مرحلة من خارطة الطريق: `git tag v0.<phase>.0 && git push --tags`.
مثلًا `v0.2.0` بعد دمج S10، وساعتها النظام يشتغل من أوله لآخره بنموذج وهمي.

## 6. قواعد ذهبية
1. **ما تفرضه أداة لا تكتبه كتعليمات:** الطبقات بـ import-linter، والجودة بـ ruff وmypy، والإنهاء بالـ Stop hook، وgit بالـ PreToolUse hook.
2. **`CLAUDE.md` قصير.** لو Claude بيتجاهل قاعدة، الملف غالبًا طويل. احذف منه بدل ما تضيف.
3. **جلسة لكل شريحة.** والبحث الطويل في الكود يروح لـ Subagent.
4. **الاختبارات تتراجع قبل الكود.** بعد Commit الاختبارات، تعديلها ممنوع إلا بـ Commit مستقل فيه السبب.
5. **التقييم ملكك.** الـ Agent يشغّل الـ Harness لكن مايعدّلش بيانات المرجع ولا العتبات.
6. **قرار جديد = ADR في نفس الفرع.** الوثيقة والكود مايختلفوش أبدًا.
